# Catalog seed/floor: derived files should not be tracked

## Problem

`registry/catalog.json` is generated by `refresh-catalog.bat` every Sunday via `catalog.py build`. Nothing ever committed it. So the file on `master` sat at its 2026-06-05 state for eleven weeks while the weekly task reported success, and the 2026-08-16 refresh was nearly lost to an auto-stash during unrelated branch work.

A tracked derived file rewritten on a schedule is a liability: it drifts invisibly, it clogs history, and it turns up dirty in every repo that has run the task.

## Decision

**`registry/catalog.json` is now gitignored**, with `registry/catalog.seed.json` as the committed floor.

- All three readers resolve **live-then-seed** and prefer the live file if it exists, falling back to the seed when the live copy is absent
- The readers are: `catalog.py`, `init_project.py`, and the `suggest-agents` hook
- The resolvers are **deliberately duplicated three ways**, not shared — each must stay importable independently
  - `suggest-agents` is a hook loaded at every SessionStart and must not depend on shared modules
  - `init_project.py` has no pattern of importing shared helpers
  - Tests assert all three resolve to the same file, catching divergence

## The seed is a floor, not a cache

Reading the seed says so on stderr — `[note] reading the committed seed (158 agents) - run 'catalog.py build' for the current upstream` — so a stale answer never passes for the current upstream. This distinction matters most in the quietest reader: if `init_project` fell back to `{}` when the catalog was missing, every catalog agent would be marked `dropped` as unknown. Without a seed, a fresh clone would silently ship projects with their agent roster stripped — the file being absent would have become a *default*, not an edge case.

**The seed moves only when asked**, via `catalog.py build --seed`. A floor that drifts on its own is not a floor.

## Implementation

- `registry/catalog.seed.json` is committed and tracks the baseline catalog
- The weekly `refresh-catalog.bat` still calls `catalog.py build`, which writes only to `registry/catalog.json` (now gitignored)
- `catalog.py build --seed` explicitly updates the seed when the baseline should move
- `test_all_three_resolvers_agree` fails if any copy drifts; the resolution-order tests are parametrized across all three readers
- The .gitignore entry for `registry/catalog.json` is committed

## Why not auto-update the seed?

A schedule that rewrites a tracked file does not work: nothing commits it, or commits pile up, or the file sits dirty. Deriving a controlled schedule (`--seed`) keeps the floor under human control.

## What deliberately does NOT exist

There is **no heartbeat check on the catalog**. The obvious one — report
`registry/catalog.json` dirty or missing — would fire every week between Sunday's
refresh and the next commit, and a permanently red line is how a gate stops being
read. The seed removes the need for one: a fresh clone always has a working
catalog, and the live file drifting is no longer a repo concern because it is no
longer in the repo.
